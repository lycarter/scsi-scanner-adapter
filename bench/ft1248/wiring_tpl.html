Why the four data wires cross

MIOSIO0–3 must land on consecutive Pico GPIOs in the same order, because a PIO program moves a nibble with one instruction. The breakout numbers D0–D3 toward its USB end and the Pico numbers GP16–GP19 away from its bottom corner, so with the boards facing each other the four wires interleave. On the breadboard they simply pass over one another.

The PCB has the same geometry: the phase 3 notes record six unavoidable MIOSIO crossings between the RP2350B and the FT232H, routed with vias. Reversing the bit order would remove them, and was rejected to keep the firmware simple.

What changes on the wires

  • A byte takes 2 clocks, a nibble each, where 1-bit took 8. At the same clock the link should carry roughly four times the data.
  • The chip chooses the width per transaction from which data lines are low on the first clock, so the EEPROM needs no change (AN_167 §4).
  • All four lines turn around together. With no series resistors, a firmware mistake can now put two outputs against each other on four pins, so the first 4-bit runs start slow, as the 1-bit ones did.
  • Unknown until measured: whether ACK on MISO is still valid only on the first clock of a byte, now that a byte is only two clocks long.

Where the bench stands

  • EEPROM programmed for FT1248: clock idles low, MSB first, flow control on, serial BENCH1.
  • 1-bit link clean at 30 MHz in both directions; reads need the RP2350 input synchroniser bypassed at that speed.
  • 100 MB sustained from Pico to Mac at 3.25 MB/s, every byte verified.
